# Future payout-runtime adoption after the narrow receipt guard

**Draft, not approval to deploy, migrate, record a receipt, schedule a worker, or move money.** The narrow guard is independently deployable after its own review and approval. This separate artifact adopts that guard into the much larger payout runtime. It is not the fast way to reconcile an individual external payment.

## Exact installation sequence and migration history

1. Merge/review the narrow guard code and its canonical CLI-generated migration `20261113074114_external_receipt_guard.sql` first. Approve its actual rollout separately. No receipt is inferred by installing it.
2. For a later approved runtime release, use this branch's chronological **`20261113074433_external_guard_runtime_adoption.sql`**, generated by `supabase migration new external_guard_runtime_adoption --workdir apps/mobile` with CLI 3.1.0. Its bytes are built by `node scripts/build-external-guard-adoption.cjs` and checked with `--check`. Tests execute this actual migration file, not a hand-written substitute.
3. The original #286 files `20261111010000_payout_readiness_observability.sql` and `20261111040111_settlement_runtime_v1.sql` are removed from executable migrations on this adoption branch. Their reviewed contents remain at `docs/payments/drafts/payout-readiness-observability.sql` and the reproducible `docs/payments/drafts/settlement-runtime-pristine.sql`. The latter is still assembled by `build-settlement-migration.mjs`; baseline runtime regressions use it. Both sources are incorporated into the new adoption transaction.
4. **Do not deploy original #286 directly after the narrow guard. Do not use indiscriminate `--include-all` or edit applied migration history.** Read-only production history on November13 showed neither retired version applied; that is not proof for every environment or for a future rollout. Revalidate the actual target history, schema and complete pending-migration plan immediately before an approved installation. If either retired version is recorded, a runtime already exists, or the target is not the exact reviewed guard schema, this installer fails closed. That environment needs its own reviewed upgrade plan.
5. If subsequent production migrations make this still-unapplied draft timestamp out of order, regenerate a new later CLI migration and update/retest this explicit contract before proposing rollout. Never bypass chronological checks to force an old draft into a newer database.

A negative test executes the exact original #286 artifact against both pending-only and completed-receipt guard fixtures. It fails inside its transaction; explicit rollback preserves the original catalog, ACLs, receipts and legacy claim exclusion. This is evidence about the original complete transactional artifact, not permission to run extracted fragments. Release safety still relies on retiring those executable files and enforcing the approved history/catalog preflight.

The artifact requires the standalone guard's canonical migration-history entry. The prerequisite file here is byte-identical to the pinned guard source. `scripts/fixtures/external-guard-adoption/contract.json` records both source commits and the exact paths. The pinned fixture is an immutable test/compiler input, not a second database ledger.

## Preservation and safety properties

- Exact catalog preflight checks the narrow private tables, columns, defaults, constraints/indexes, RLS, client permissions, function definitions, triggers and ledger-reference constraint. Unknown objects, weakened permissions, changed code or a disabled trigger require a fresh review; they are not silently accepted with `IF NOT EXISTS`.
- Receipt IDs, request/provider references, immutable evidence, original ledger economics, recipient identity, reported-but-unverified source snapshots, recovery history and event exclusions stay in their existing canonical tables. There is no rename/copy to another ledger, no empty runtime stub table and no deletion of existing evidence.
- Pending event quarantines remain permanent even with no receipt or after only some captured rows are reconciled. Updating an ordinary event hold or release date cannot clear them. The runtime cannot admit checkout/source allocations or reserve promoter **or host** transfers for those events.
- Every new runtime admission/reservation takes the event boundary before source/control locks, matching report/record ordering. A report racing an already-reserved transfer does not pretend it never existed. It returns review-required; reconciliation of that already-sent or uncertain attempt remains possible. This is not cross-provider exactly-once payment execution and cannot undo a Cash App/Stripe payment already sent concurrently.
- Incident-scoped operators, expiring drain/source-risk attestations, exact captured ledger scope, actual session-row identity/expiry checks, final post-wait authorization checks and source immutability remain enforced. Raw receipt/report/status RPC execute privileges remain revoked even from `service_role`; only the session-bound wrappers retain their reviewed grant. All private runtime helpers remain non-executable by application roles.
- **Both receipt/report operator gates and every financial runtime gate are off after adoption.** Existing records, identities and audit evidence remain intact. No scheduler is installed and no provider API is called.
- The adoption intentionally preserves the narrow legacy claimant's original `processing` semantics instead of #286's `on_hold` claim change. With the current live payout-status constraint, unaffected legacy claims still fail safely. Protected events remain excluded even if a later reviewed change permits `processing`. This adoption does not repair or activate general legacy aggregate payouts, and historical destination-funded organizer amounts are not authorized to be paid again.

## Maintenance and activation gates

The transaction uses bounded lock acquisition and takes exclusive locks over the event/source/ledger/attribution/payout/promoter and narrow-guard tables before catalog/data validation. Plan a maintenance/drain window; a lock timeout rolls back instead of waiting indefinitely. In-flight external provider calls cannot be canceled by a database lock. Drain and reconcile them independently before any approved installation. Concurrent administrative schema/permission changes are not supported.

A future runtime release still needs its own complete current-master composition, provider adapter/worker/webhook tests, account and funding proof, physical balance/sweep policy, runtime budget and scheduler validation, alert delivery, eligible cohort approval, financial-action confirmation and production approval. Passing these SQL tests does not certify a real bank payout or authorize enabling a gate.

Before any SQL the runner rejects routing variables, non-GitHub-hosted execution, wrong image/purpose/network/privileges and persistent mounts.
