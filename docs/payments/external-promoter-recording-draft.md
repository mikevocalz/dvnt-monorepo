# External promoter payment recording: draft only

This change records an **already completed, independently reviewed external payment**. It does not make a payment, assert that any real person has been paid, or initiate a deployment, migration, scheduler, reversal, or funds movement. No live identifiers belong in this artifact.

## Boundaries and prerequisites

- Stack this additive work on paused checkpoint `f38034ca`. The shared checkpoint branch is not a release: its aggregate migration is empty and its existing release-policy, integration, monitoring and sandbox gates remain open. Do not merge/deploy it or replace the existing foundation PR on this evidence.
- Test SQL load order: settlement ledger, runtime, recovery, observability, then `settlement-external.sql`. The application schema must already include promoter attributions/ledger payout fields and payouts. The optional promoter-first change calls the overridden `promoter_obligation_satisfied` helper and skips externally satisfied promoter obligations without changing host allocations.
- This is **historical bookkeeping, not a safe future manual-payment executor**. Atomic receipt recording cannot prevent a Stripe payout racing an external payment that happened before recording. A conflicting Stripe reservation makes recording fail; it cannot undo two already completed payments. Before any future external payment, separately authorize it, disable/drain automated execution, review in-flight and uncertain transfers, and retain independent evidence. A prepared external-payment intent that reserves exact obligations before payment is a separate prerequisite for automating that workflow. No exactly-once cross-provider guarantee is claimed here.
- Before installing recording guards, drain old workers and audit old in-flight/uncertain outcomes. Existing claims are not reconstructed. Upgrade every conservative `on_hold` claimant to `settlement_claim_legacy_event`. A still-running pre-change worker that has already passed its claim is not made safe retroactively by this SQL.
- The endpoint defaults off. The private operator allowlist defaults empty. A separately reviewed administrator must configure authorized operators and independently verified opaque recipient bindings. Event owners, co-organizers and promoters have no inherent recording permission.

## Evidence and authorization

The operator endpoint derives its actor from the verified session, rejects a body-supplied actor, checks private operator authorization and calls a service-only transaction. Service credentials and operator provisioning remain trusted administrative boundaries, not client credentials.

The operator must independently check an authentic provider receipt against the exact recipient binding, transaction reference, completed final status, amount, currency and actual payment time. Retain receipt bytes as an access-controlled immutable object/version before recording. Provide its opaque reference and SHA-256 digest. References must have exactly three relative segments, namespace/object/version: lowercase namespace followed by alphanumeric, underscore, hyphen or dot object/version tokens. URLs, whitespace, email addresses and dot-segment paths are rejected. Do not put sensitive data inside these tokens. Do not include bank account details, public receipt URLs, raw receipts or provider secrets. The explicit manual attestation is mandatory. Pending, failed, reversed, unverified or incomplete evidence does not qualify. A platform balance top-up is not a payment to a promoter.

**A digest and immutable audit trail establish integrity, not provider payment authenticity.** This draft records an authorized human's verification; it does not fetch or cryptographically authenticate arbitrary external-provider receipts. Storage retention and independent receipt review must be validated operationally before enabling it. UI wording is “Paid externally (receipt manually verified),” never “Stripe transfer” or “verified bank payout.”

## Atomic guarantees after recording

- Locks the event, source orders in deterministic order, shared funding controls and exact ledger rows. Validates row count, positive earning-only scope, amount sum, attribution, event, promoter, currency, order payment state, absence of reversal/refund/dispute holds, and absence of reserved/uncertain/transferred promoter execution.
- Records unique request key, provider transaction, receipt digest, immutable recipient/economic snapshots and operator attestation. Exact replay returns the same record; changed scope/evidence fails. Receipt/transaction reuse across obligations fails. Multi-row stamping, audit, exclusion and funding epoch update commit or roll back together.
- Leaves original earnings intact. Stamps settled ledger rows without fabricating any Stripe identifier. These stamps and legacy source economics cannot later be erased or reparented to escape exclusion. Later reversal entries and refund/dispute bookkeeping remain possible.
- A promoter delivery trigger and the shared source-order lock prevent any new Stripe reservation after recorded external settlement. The promoter-first helper recognizes only exact immutable scope, and does not satisfy recovery-held/reversed obligations. The funding epoch invalidates prior balance observations.
- The whole event gains a permanent legacy aggregate exclusion independent of mutable event hold/release status. The legacy eligibility read, new atomic claim, old `processing` claim trigger and payout write trigger reject subsequent aggregate funding. A normal dispute hold may clear/reappear without removing that exclusion. Historical destination-funded orders still cannot enroll in the separate-charge engine; external proof does not authorize paying the host again.
- The protected nullable ledger `external_settlement_id` supports exact legacy/new/external UI partitions without subtracting original earnings. Private receipts and references are never returned to promoter/organizer read models. Frozen promoter identity receives an aggregate external status; later refund, dispute or ledger reversal raises a review label. External proof is not Stripe bank-payout membership.

## Validation

The offline suite executes actual draft SQL in PGlite and tests receipt replay/reuse, changed scope, unauthorized roles, invalid/no evidence, rollback, existing Stripe reservations, post-record Stripe rejection, legacy exclusion after hold clearing, receipt privacy and truthful UI labels. Endpoint tests execute the actual handler with mocked auth/database boundaries and verify actor derivation, default-off gating and error redaction.

`test-external-settlement-concurrency.py` exercises nine real PostgreSQL cross-process races in disposable CI databases: same-key replay, different-key overlap, receipt reuse, both Stripe/external orderings, both legacy/external orderings after hold clearing, and bank-proof/failure versus refund lock ordering. It refuses to run against a developer/production database. Local PGlite results are not proof of cross-process locking. No real provider sandbox execution is included; CI and final integrated migration compatibility must be reviewed independently.

## External recovery contract

Later order refunds, partial refunds, disputes, cancellations, settlement holds or ledger reversals append immutable `external_recovery_reviews` provenance. `settlement_external_recovery_candidates` returns the typed action `manual_external_payment_recovery_review`; no provider reversal is attempted or invented. `settlement_external_recovery_health` counts distinct affected orders as `external_recovery_review_required`. These reviews never silently clear when an order/event changes back. An authorized, evidence-backed manual recovery/resolution workflow is still required before any such obligation can be considered settled again; no resolution API is provided here.

Local focused verification at this commit: 50/50 receipt/endpoint/legacy/UI tests passed; isolated handler/shared-display TypeScript check passed. The native race runner compiled and correctly refused non-CI execution. Cross-process results remain pending CI. These checks do not certify the inherited checkpoint or production rollout.

Identity and hold hardening: receipt beneficiary bindings include immutable recipient-user identity; current promoter reassignment cannot pay or expose a frozen earlier recipient obligation, including before enrollment. Pre-enrollment refund/dispute/manual checkout holds also append explicit manual recovery provenance. Bank-only proof/failure writes do not acquire an inverted source lock.
