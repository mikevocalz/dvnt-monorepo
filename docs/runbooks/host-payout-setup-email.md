# Host Stripe setup reminder email (operator-only)

The existing app modal shows organizer or promoter onboarding status. This email is a separate one-time organizer-only reminder for the owner of an explicitly selected upcoming public, visible, active event with an active paid tier whose sale has not closed. It never handles promoter commissions, Stripe bank payouts, ticket receipts, balance, or release. No automatic scheduling or batch endpoint. Private/link-only, free-only, hidden, unpublished, canceled, started, opted-out, banned and unverified cases are excluded. Historical earnings remediation is out of scope.

Growth outbox is intentionally not reused: its generic sweep and retry behavior are not the authorization or duplicate-prevention contract for this one recipient-bound transactional notice. Attendee reminder rows bind purchased tickets and must not be repurposed. This feature's distinct additive migration is a **release prerequisite**, not production-applied by this work.

## Preview and explicit dispatch
1. A separately approved rollout applies only `20261124162500_host_payout_setup_email.sql` and deploys `host-payout-setup-email` and its shared imports. Keep send disabled until the owner approves the operator workflow; preview works without enabling send. Do not deploy it separately from a requested aggregate release.
2. A trusted operator makes a service-credential-authenticated POST to `/functions/v1/host-payout-setup-email` with `{"mode":"preview","eventId":123}` using an approved event ID. Preview reads only, and returns the exact verified owner address, message and fingerprint for separate review. Never expose it to the app or accept caller-supplied addresses. Confirm approval of the specific recipient and email.
3. Only with that approval and explicit release enablement, dispatch one POST with `{"mode":"send","eventId":123,"approvalFingerprint":"<approved preview fingerprint>"}`. Runtime requires `DVNT_HOST_PAYOUT_SETUP_EMAIL_ENABLED=true`, existing live Stripe and Resend configuration, and the service credential. Do not export credentials. The fingerprint is not authorization. The service-level operator is accountable for approval.
4. Send rechecks current ownership, eligibility, verified address, Stripe account metadata/requirements and selects only the exact approved scope. Explicit Stripe review, unavailable status and rejected accounts do not trigger setup email. When no explicit review blocks the account, an overlap between due and pending-verification fields is not a new user action; a separate due requirement can still qualify. Claim is unique per host across events and suppresses all repeats. A missing or uncertain provider result leaves a permanent claim; resolve against original provider logs before any further human action. A provider acceptance is not inbox delivery. Never create a replacement ledger row to retry.

No Stripe writes, provider invocation, email enqueue, repeated reminders or finance changes happen during preview or fixture tests. Email setup is not proof that a Stripe transfer to a promoter is payable. Fixtures do not exercise the live Edge auth provider, Stripe account, Resend sender or local inbox delivery.
