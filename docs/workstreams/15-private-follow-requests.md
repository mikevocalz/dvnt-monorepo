# Private page follow requests

Private access requires a live follow and one of three honest authorization sources:

- `follow_requests.status = 'approved'`: the owner actually approved the request.
- `follow_legacy_access`: the relationship existed at the one-time preservation boundary.
- `public_follow_acceptances`: this exact relationship was accepted while the owner was Public.

The cutover preserves **all existing relationships**, including Public accounts later made Private, without modifying follows/counts or inventing an owner approval. Every subsequent Public follow also retains access after a later Private choice. Every new follow to an already-Private account needs approval. Public acceptance and legacy preservation are recorded separately from approval, tied to the exact `follows.id` incarnation.

`follow` on a retained relationship is idempotent and creates neither a request nor a notification. `unfollow` cancels pending requests and removes the relationship. `status` reports retained access as `following: true` with request status `none`, not fabricated `approved`. Older clients may omit action for a serialized toggle. `requests` lists the caller's oldest 100 pending requests. For approve/decline, the owner is always the verified caller.

Deletion, owner removal, or changing id/follower/following retires both preservation/acceptance grants and old request authorization. Re-follow, same-id reinsertion, backdating and rerunning the cutover never restore retired authorization. The one-shot batch records capture time/count, migration identity and `legacy_access_preservation` provenance. Application services can read grants/batches but cannot write or recapture them. Keep real relationship IDs in the restricted database, never repository artifacts.

Bilateral blocks continue to win while active. Blocking does not silently delete follows; unblocking restores only otherwise-valid access. Existing age/admission, moderation and visibility checks remain independent. Malformed non-false privacy preferences fail closed. The database insert guard covers verified RPCs and direct service/brand writers: a new Private follow becomes a pending request without inserting a follow or changing counts. Public inserts record acceptance. Brand writers still return successful zero-row counts for pending relationships and can retry idempotently.

## Additive rollout, then atomic activation

This source is not permission to deploy or execute production SQL. Do not combine these phases in a bulk database push.

1. Complete the release checklist's trusted identity and guarded auth-sync/CAS settings prerequisites. Apply `20261109110000_private_follow_requests.sql` as an **additive compatibility phase**. It creates a `ready=false` batch, empty grant tables and compatible RPCs. It captures no relationships and does not yet revoke direct follow writes. Before readiness, the mutation RPC retains legacy immediate follows, and the Edge projection skips the newly introduced follow/private restrictions. Existing block, age/admission and content checks remain. A missing compatibility schema is an error, not permission for a broad fallback.
2. Deploy and verify the compatible `toggle-follow` and every service-role post reader listed in the release checklist. Keep the old deployed version identifiers and new reviewed source/handler hashes in the release ledger. Replace all writers/readers before activation; drain old Edge invocations **and their outstanding database requests/transactions** using the platform's verified deployment/drain process. New requests continue through the compatible versions. Never deploy the earlier approved-only weekly reader: it lacks compatibility mode and would deny existing followers. If complete version replacement/draining cannot be established, stop here with `ready=false`; do not invent a maintenance hold or silently activate.
3. Apply `20261109114000_post_follow_read_gate.sql` after the guarded settings writer is verified. It installs the privacy-sync trigger and restrictive policies, but their new follow predicate remains inactive while `ready=false`, so older RLS remains authoritative. It records `read_gate_version=1` only after the complete matching gate is installed. Public acceptance starts only after activation, when settings changes and follow inserts serialize through owner-row locks.
4. Verify compatibility reads/mutations, unchanged existing follow counts, empty preservation grants, all deployed handler versions and no outstanding old requests. Record the exact reviewed commit and migration/cutover SHA-256 hashes, project, operator authorization reference, and drain evidence in the restricted release ledger. Obtain separate approval for the named project's cutover and direct-client permission changes.
5. Execute only `docs/security/private-follow-preservation-cutover.sql`. The bounded write barrier locks users, settings, follows, blocks, requests and all grant/audit tables in a fixed order. It verifies the staged gate protocol and enabled privacy trigger, snapshots **all live follow IDs**, closes direct client follow writes (including column grants and verified effective inherited privileges), and flips `ready=true` in one transaction. Compatible readers continue serving: each statement sees either compatibility mode or completed preservation. Queued mutation RPCs obtain a conflicting table lock before reading readiness, so they cannot carry a stale compatibility flag across the switch. Direct inserts likewise join the follow-table barrier. Follow mutations support READ COMMITTED (the normal service transaction mode); INSERT, identity UPDATE, DELETE and mutation RPCs reject REPEATABLE READ/SERIALIZABLE with `40001` so stale snapshots cannot transfer or restore grants. Retry only in a fresh READ COMMITTED transaction.
6. After commit verify the batch/count, protocol/readiness, client privileges, retained relationships, new Private pending behavior, Public-to-Private retention, blocks, age, owner removal and service/RLS parity. Record aggregate evidence only. Ship matching clients after the separate staging/native acceptance checks.

The five-second lock timeout/thirty-second statement timeout bounds a contested cutover. On timeout roll back and investigate the competing writer before retrying. The prior compatibility state remains available. After an uncertain outcome inspect the batch/ledger first: a successful batch must never be deleted or recaptured. A rerun cannot include late/backdated/reinserted rows. A rolled-back first attempt may retry. A post-COMMIT schema-notification failure is not proof of rollback.

After activation, repair forward; never restore a legacy reader, direct follow writes, or `ready=false`. An older client must use the compatible service endpoint; unsupported direct database writes are deliberately closed. Previously delivered media and known public asset URLs are not revoked by database checks.
