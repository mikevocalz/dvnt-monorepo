path without reading where it led.** The audit that found the refund call ran

## 5. Traps that cost me time

- **The Supabase MCP renders results as an artifact the caller cannot read.**
  Workaround that always works: wrap the query in a `DO $$ … RAISE EXCEPTION
  '…%…', val; END $$;` block. Errors render inline; results do not.
- **A failed `curl` is not a changed value.** My first deploy watcher used
  `until [ "$cur" != "$before" ]`, and an empty string from a timed-out request
  satisfied it. It reported a deploy live that had not happened. Require
  non-empty AND different.
- **`dvntapp.live` will 403 `curl` with `x-vercel-mitigated: challenge`** if you
  poll it. That is Vercel's firewall JS challenge, not an outage — browsers pass
  it transparently. Do not poll the apex; use `www` and a 30s interval.
- **Typecheck and unit tests do not render components.** I shipped React error
  #310 (hooks below an early return) with 676 tests green. **Open the page.**
- **`hours_back` in `reconcile-orders` is a MINIMUM AGE** (`.lt(created_at,
  cutoff)`), not a window. Small values widen the sweep.
- **`tickets.user_id` holds two id namespaces.** Better Auth id (what
  checkout/RSVP write, 305/308 rows) and historically the `users.id` integer.
  `resolveTicketAccess` accepts either via `viewerAuthId`.
- **Sessions persisted before 2026-09-18 carry no `authId`.** `useTicketViewerAuthId`
  backfills it from `getCurrentUserRow()` and writes it back. Do NOT bump the
  auth-store persist version to fix this — it signs everyone out, and
  `02-after-saturday-web-session-fix.patch` is on the do-not-deploy list for
  exactly that.

## 10. Guest ticket-email delivery hardening + staff/promoter pickers (2026-09-21)

### Email pipeline audit verdict

The rails already sent ONE `ticketConfirmation` email per fulfillment call
containing all newly-inserted tickets — the "only tickets[0]" failure did
not exist. The real gaps, all fixed below:

- **Partial-replay bundle loss**: the email was built from *this call's*
  inserted rows. A crash mid-insert then a webhook replay would email
  only the rows inserted on the retry, not the full order. Fixed: the
  email is always built from the order's authoritative ticket set.
- **No delivery state**: Resend failure was a console.log — permanent,
  silent, unretryable. Fixed: `orders.ticket_email_*` columns +
  reconcile sweep + webhook-replay self-heal.
- **No order↔ticket link**: tickets related to orders only via Stripe
  ids; free door tickets had NO link. Fixed: `tickets.order_id` column,
  backfilled, stamped on all new rows (session rail, PI rail, free RPC).
- **Raw QR token printed in email body**: removed — the signed token is
  a credential; the per-ticket lookup link is the images-off fallback.
- **No staff resend**: guests had `guest-ticket-lookup` self-serve, staff
  had nothing. Fixed: `door-sell` `action:"resend"` (staff-scoped,
  re-emails existing bundle only — never mints/charges).
- Per-ticket tier/name metadata: the bundle now carries each ticket's
  own tier name/category + attendee_name (mixed-tier safe), not one

- Note: cart rail sends no email at all — it's authenticated-only
